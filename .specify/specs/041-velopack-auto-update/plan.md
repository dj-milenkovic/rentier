# Implementation Plan: Velopack Auto-Update

**Branch**: `041-velopack-auto-update` | **Date**: 2025-07-14 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `.specify/specs/041-velopack-auto-update/spec.md`

## Summary

Implement auto-update functionality for Rentier using the Velopack framework (MIT license, cross-platform). The feature adds: (1) Velopack lifecycle hooks in `Program.cs` for install/update/uninstall events, (2) an `IUpdateService` Application-layer interface with `VelopackUpdateService` Infrastructure implementation using `GithubSource`, (3) a reactive notification bar in `MainWindow` driven by `MainWindowViewModel` that shows update availability, download progress, and restart prompts, and (4) full DI registration following existing project patterns.

## Technical Context

**Language/Version**: C# 12 / .NET 8  
**Primary Dependencies**: Velopack (NuGet), Avalonia UI 11+, ReactiveUI, Microsoft.Extensions.DependencyInjection  
**Storage**: N/A — no database entities; all state is transient/session-scoped  
**Testing**: xUnit + FluentAssertions + NSubstitute  
**Target Platform**: Windows + macOS (cross-platform via Avalonia)  
**Project Type**: Desktop application (Avalonia)  
**Performance Goals**: Update check completes within 10 seconds of app launch; zero perceptible startup delay  
**Constraints**: No user data transmitted; GitHub public API rate limit (60 req/hour unauthenticated); offline-resilient (silent failure)  
**Scale/Scope**: Single-user desktop app; one update check per launch

## Complexity Tracking

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Constitution amendment: adding GitHub API to approved network endpoints | Auto-update requires checking GitHub Releases for new versions and downloading assets. This is the only viable public distribution channel for the project. | Removing auto-update entirely would sacrifice significant user value. Manual download is error-prone and discourages adoption. |
| Velopack package referenced in both Desktop and Infrastructure | `VelopackApp.Build().Run()` MUST be in `Program.cs` (process entry point, before DI); `VelopackUpdateService` MUST be in Infrastructure (implements Application contract) | Single-project reference is impossible: lifecycle hooks require process-level code in Desktop; service implementation belongs in Infrastructure per Clean Architecture. The Desktop reference is for the 3-line lifecycle bootstrap only — no service-level Velopack usage. |
