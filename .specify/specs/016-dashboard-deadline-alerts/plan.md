# Implementation Plan: Dashboard with Deadline Alerts

**Branch**: `005-dashboard-deadline-alerts` | **Date**: 2025-07-18 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `.specify/specs/016-dashboard-deadline-alerts/spec.md`

---

## Summary

Add a Dashboard screen as the default landing view in Rentier. The dashboard provides at-a-glance
visibility into upcoming filing deadlines (next 30 days), overdue filings (past deadline, not paid),
summary statistics (counts by status, total unpaid RSD), and last mailbox sync date. This is a
**read-only** feature — no schema changes, no mutations, no EF migration.

The feature spans three layers (no Domain changes):

- **Application**: New `GetDashboardQuery` + handler, three DTOs (`DashboardDto`,
  `UpcomingDeadlineDto`, `OverdueFilingDto`), and three new `IFilingRepository` methods
  (`GetUpcomingAsync`, `GetOverdueAsync`, `GetFilingStatsAsync`).
- **Infrastructure**: EF Core implementations of the three new repository methods. No migration.
- **Desktop**: New `DashboardViewModel` (IActivatableViewModel) + `DashboardView.axaml`,
  two row ViewModels, navigation wiring in `MainWindowViewModel`, DI registration in
  `CompositionRoot`, and new string resources.

## Technical Context

**Language/Version**: C# 12 / .NET 8  
**Primary Dependencies**: Avalonia UI 11, ReactiveUI, EF Core 8 (SQLite), Microsoft.Extensions.DependencyInjection  
**Storage**: SQLite via EF Core; read-only queries on existing `Filings` and `Mailboxes` tables  
**Testing**: xUnit + FluentAssertions + NSubstitute; SQLite in-memory for infrastructure tests  
**Target Platform**: Windows + macOS desktop (cross-platform Avalonia)  
**Project Type**: Desktop application (Avalonia MVVM)  
**Performance Goals**: Dashboard load ≤ 2 s for up to 10,000 filings (SC-006)  
**Constraints**: No UI thread blocking; all I/O via `async Task`; `decimal` for money; `DateOnly` for dates; no EF migration  
**Scale/Scope**: Single-user SQLite; 30-day upcoming window naturally limits result set

## Phase 0: Research

> All NEEDS CLARIFICATION items were resolved in `clarify.md` and `research.md` via spec
> clarification and static codebase analysis. No external research or tooling decisions are blocked.

### R-001 — Repository Strategy for Dashboard Queries

**Decision**: Add three purpose-built methods to `IFilingRepository`: `GetUpcomingAsync`, `GetOverdueAsync`, `GetFilingStatsAsync`.  
**Rationale**: Pushes filtering to SQL; avoids loading full table. `GetFilingStatsAsync` computes counts/sum at DB level.  
**Alternatives rejected**: (1) `GetAllAsync` + in-memory — unnecessary memory allocation. (2) Single monolithic query — poor testability.

### R-002 — LastSyncDate Resolution

**Decision**: LINQ over `IMailboxRepository.GetAllAsync()` results — select max `Cursor.LastSyncDate`.  
**Rationale**: 0–2 mailboxes typical; handler-side LINQ is simpler than a new repository method.  
**Confirmed**: `MailboxCursor` is `record(DateOnly? LastSyncDate, long? LastUid)` — simple record, not discriminated union.

### R-003 — ViewModel Injection Pattern

**Decision**: `ActivatorUtilities.CreateInstance<DashboardViewModel>(provider, navigateToFilings)` in `MainWindowViewModel`.  
**Rationale**: `DashboardViewModel` needs `Action navigateToFilings` that closes over `MainWindowViewModel` state. Mirrors `ReportsViewModel` pattern.

### R-004 — NavigateToFilings Delegate

**Decision**: `Action navigateToFilings` (no parameters). Navigates to Filings pane without filtering.  
**Rationale**: FR-020 requires pane switch only — no filing selection.

### R-005 — Monetary Display

**Decision**: `CultureInfo.InvariantCulture` with `$"{value:N2} RSD"` format.  
**Rationale**: Explicit architecture constraint; deterministic formatting.

### R-006 — Auto-Refresh on Navigation

**Decision**: `IActivatableViewModel` + `WhenActivated` triggers `LoadCommand.Execute()`.  
**Rationale**: Matches `FilingsViewModel` pattern; guarantees data freshness.

### R-007 — No Schema Changes

**Decision**: No EF migration. FR-018 explicit.

### 1.3 Infrastructure Layer

#### `FilingRepository.GetUpcomingAsync` implementation

```csharp
public async Task<IReadOnlyList<Filing>> GetUpcomingAsync(
    DateOnly today, int days, CancellationToken ct = default)
{
    var end = today.AddDays(days);
    var list = await _db.Filings
        .AsNoTracking()
        .Where(f =>
            (f.Status == FilingStatus.Init || f.Status == FilingStatus.Filed) &&
            f.FilingDeadline >= today &&
            f.FilingDeadline <= end)
        .OrderBy(f => f.FilingDeadline)
        .ToListAsync(ct);
    return list.AsReadOnly();
}
```

#### `FilingRepository.GetOverdueAsync` implementation

```csharp
public async Task<IReadOnlyList<Filing>> GetOverdueAsync(
    DateOnly today, CancellationToken ct = default)
{
    var list = await _db.Filings
        .AsNoTracking()
        .Where(f =>
            (f.Status == FilingStatus.Init || f.Status == FilingStatus.Filed) &&
            f.FilingDeadline < today)
        .OrderBy(f => f.FilingDeadline)
        .ToListAsync(ct);
    return list.AsReadOnly();
}
```

#### `FilingRepository.GetFilingStatsAsync` implementation

```csharp
public async Task<(int InitCount, int FiledCount, int PaidCount, decimal TotalUnpaidRsd)> GetFilingStatsAsync(
    CancellationToken ct = default)
{
    var filings = await _db.Filings.AsNoTracking().ToListAsync(ct);

    var initCount = filings.Count(f => f.Status == FilingStatus.Init);
    var filedCount = filings.Count(f => f.Status == FilingStatus.Filed);
    var paidCount = filings.Count(f => f.Status == FilingStatus.Paid);
    var totalUnpaidRsd = filings
        .Where(f => f.Status != FilingStatus.Paid)
        .Sum(f => f.TaxPayableRsd);

    return (initCount, filedCount, paidCount, totalUnpaidRsd);
}
```

> **Note**: For ≤10,000 filings (single-user app), in-memory aggregation after a single
> `SELECT *` is acceptable and avoids complex grouped SQL that SQLite may not optimise well.
> If performance becomes an issue, this can be refactored to use `GroupBy` with server-side
> aggregation without changing the interface.
