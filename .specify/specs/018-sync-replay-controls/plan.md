# Implementation Plan: 018 Sync Replay Controls

**Branch**: `feature/018-sync-replay-controls` | **Date**: 2025-07-15 | **Spec**: `.specify/specs/018-sync-replay-controls/spec.md`
**Input**: Feature specification from `.specify/specs/018-sync-replay-controls/spec.md`

## Summary

Add sync mode selection (Incremental, Replay from Date, Full Replay) and duplicate handling strategies (Skip Existing, Create New Revision, Reprocess in Place) to the sync pipeline. Remove the deprecated `InitialSyncDate` field from the Mailbox entity—superseded by the Replay from Date mode which provides the same capability more flexibly. Cursor transitions become deterministic with monotonic advancement and comprehensive logging.

| Decision | Justification |
|----------|--------------|
| SyncParameters in Domain (not Application) | It contains domain concepts (SyncMode, DuplicateStrategy) and is used by domain entity methods (cursor logic). Placing in Domain preserves inward-only dependencies. |
| OriginalReportId self-referencing FK on Report | Simplest way to track revisions without a separate entity. The FK is nullable and optional — does not complicate existing Report usage. |

## Architecture Decisions

### AD-001: SyncParameters as Domain Value Object

**Decision**: `SyncParameters` is a `sealed record` in `Rentier.Domain/ValueObjects/` containing `SyncMode`, `DuplicateStrategy`, optional `DateOnly? ReplayFromDate`, and optional `Guid? ScopeImporterId`.

**Rationale**: The sync mode and duplicate strategy are domain concepts that affect how entities are created and updated. The `GetEffectiveStartDate(MailboxCursor)` method encapsulates the domain rule for query start position. Placing in Domain allows the Application layer to pass it through without infrastructure awareness.

**Alternative rejected**: Putting SyncParameters in Application — would force Domain entities to depend on Application layer for cursor logic, violating Clean Architecture inward-only rule.

### AD-002: Cursor Override via External Parameter (Not Cursor Mutation)

**Decision**: `MailboxCursor` is NOT modified. Replay override is external — `SyncParameters.GetEffectiveStartDate()` returns the effective date, and the sync service uses that instead of reading from cursor directly for query construction. Cursor is only updated on successful completion via `max(current, new)`.

**Rationale**: Keeps `MailboxCursor` as a pure position tracker with single responsibility. No risk of persisting a "temporary" override. The cursor is always the source of truth for "where we are", while `SyncParameters` determines "where to start this run from".

### AD-003: Monotonic Cursor Advancement

**Decision**: Cursor update formula is `new = (max(old.Date, computed.Date), max(old.Uid, computed.Uid))`. Cursor never regresses. Cursor is not updated on failure or cancellation.

**Rationale**: Prevents the scenario where a replay to an older date accidentally resets the cursor, causing the next incremental sync to re-fetch old emails. The max() guarantee ensures incremental sync always starts from the furthest point reached.

### AD-004: Report Revision Tracking via Self-Referencing FK

**Decision**: Add `OriginalReportId` (nullable Guid FK to self) on `Report` entity. Originals have `OriginalReportId = null`. Revisions point to their original.

**Rationale**: Simplest schema change that enables revision tracking without a separate entity or join table. The FK with `ON DELETE SET NULL` ensures revisions survive even if the original is deleted.

### AD-005: InitialSyncDate Removal with Data Preservation

**Decision**: Migration `0010_SyncReplayControls` copies `InitialSyncDate` to `Cursor_LastSyncDate` for un-synced mailboxes (where cursor date is null), then drops the column. New mailboxes get a default cursor of 90 days before creation.

**Rationale**: Preserves the user's intended start date for mailboxes that haven't synced yet. Already-synced mailboxes don't need it (cursor has moved past). The 90-day default is a reasonable balance between completeness and performance.

### AD-006: Duplicate Strategy Dispatch at Sync Service Level

**Decision**: Duplicate detection and strategy dispatch happen in `ImapMailboxSyncService` at the point where reports are created. The existing `ExistsByImporterAndNameAsync` check is extended with strategy-specific branches.

**Rationale**: This is the natural decision point — right after an attachment is matched but before a Report is created. The strategy determines what happens when a duplicate is found. Keeping this logic in the Infrastructure sync service (not Application handler) is appropriate because it's interleaved with IMAP message processing.

### AD-007: ReprocessInPlace Safety Check

**Decision**: Before "Reprocess in Place" overwrites an existing report's filings, check `HasAdvancedFilingsAsync(reportId)`. If any filing has `Status != Init` (has been Filed or Paid), fall back to CreateNewRevision and warn the user.

**Rationale**: Filed or Paid filings represent completed tax submissions. Overwriting them could cause discrepancies with official records. The automatic fallback to CreateNewRevision preserves data integrity while still providing replay benefits.

### AD-008: SyncView UI Layout for Mode Selection

**Decision**: Extend the existing SyncView with a configuration panel above the log area:
1. **Row 0**: Mode selector ComboBox + date picker (conditional) + strategy selector (conditional)
2. **Row 1**: Impact preview panel (read-only summary of what will happen)
3. **Row 2**: Start/Cancel buttons (existing)
4. **Row 3**: Progress log (existing)
5. **Row 4**: Summary/error (existing)

**Rationale**: Keeps configuration at the top where users make decisions before starting. The impact preview below the selectors gives immediate feedback. Existing log and summary sections remain at the bottom. No new views or dialogs needed (except the Full Replay confirmation).
