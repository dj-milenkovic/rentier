# Implementation Plan: One-Click Sync Workflow

**Branch**: `015-one-click-sync-workflow` | **Date**: 2025-07-14 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `.specify/specs/015-one-click-sync-workflow/spec.md`

---

## Summary

Add a dedicated Sync pane to the sidebar that orchestrates the existing mailbox sync and report
processing steps into a single-click workflow. The feature spans two Clean-Architecture layers:

- **Application**: New `SyncAllCommand` (parameterless), `SyncAllResult` DTO, `SyncProgressEntry` DTO
  with severity enum, dedicated `ISyncAllCommandHandler` interface (not `ICommandHandler<TCmd, TResult>`
  — the standard interface cannot carry `IProgress<SyncProgressEntry>`), and `SyncAllCommandHandler`
  implementation that delegates to existing `SyncMailboxCommandHandler` and
  `ProcessReportsCommandHandler` without modifying them.
- **Desktop**: New `SyncViewModel` (IActivatableViewModel, ReactiveCommand.CreateFromTask), new
  `SyncView.axaml`, new `SyncProgressEntryViewModel` for display binding, updated
  `MainWindowViewModel` to insert a Sync `NavigationEntry` between Reports and Settings, updated
  `CompositionRoot` with `ISyncAllCommandHandler` registration.

**No Domain or Infrastructure changes**. No EF migration. Orchestration-only feature that composes
existing handlers.

---

## Technical Context

**Language/Version**: C# 12 / .NET 8  
**Primary Dependencies**: Avalonia UI 11, ReactiveUI, Microsoft.Extensions.DependencyInjection  
**Storage**: No new storage — orchestration delegates to existing handlers that write to SQLite via EF Core  
**Testing**: xUnit + FluentAssertions + NSubstitute  
**Target Platform**: Windows + macOS desktop (cross-platform Avalonia)  
**Project Type**: Desktop application (Avalonia MVVM)  
**Performance Goals**: First progress entry within 2 s of click (SC-002); cancel confirmation within 3 s (SC-004); post-sync navigation within 1 s (SC-005)  
**Constraints**: No UI thread blocking; all I/O via `async Task`; cancellation via `CancellationToken`  
**Scale/Scope**: Single-user; typical sync processes 1–10 mailboxes, 0–50 reports per run

## Phase 0: Research

> All unknowns were resolved in `clarify.md` via static codebase analysis before planning.
> No external research or tooling decisions are blocked. The findings are consolidated here
> for traceability.

### R-001 — `SyncMailboxCommand` progress injection pattern (resolved in clarify.md §Q3)

**Decision**: `SyncMailboxCommand` receives `IProgress<SyncProgress>?` via its constructor parameter (`Progress`), not as a method argument on `HandleAsync`.  
**Rationale**: Confirmed from source — `public sealed record SyncMailboxCommand(IProgress<SyncProgress>? Progress = null);`. The handler accesses `command.Progress` and passes it to `_syncService.SyncAsync()`.  
**Implementation note**: `SyncAllCommandHandler` creates an internal `Progress<SyncProgress>` adapter that converts each `SyncProgress` report into a `SyncProgressEntry` forwarded to the outer `IProgress<SyncProgressEntry>`, then passes it as `new SyncMailboxCommand(internalProgress)`.

### R-002 — Handler interface pattern (resolved in clarify.md §Q3)

**Decision**: Dedicated `ISyncAllCommandHandler` interface with `IProgress<SyncProgressEntry>` parameter — does NOT implement `ICommandHandler<TCmd, TResult>`.  
**Rationale**: `ICommandHandler<TCommand, TResult>` signature is `HandleAsync(TCommand, CancellationToken)` — no room for `IProgress<T>`. Adding progress would require modifying the base interface and breaking all existing handlers.  
**Alternatives considered**: (1) Add progress to `SyncAllCommand` record — rejected because records should be immutable data; `IProgress<T>` is a callback, not data. (2) Extend `ICommandHandler` with a progress overload — rejected because it affects all handlers and violates ISP.

### R-003 — `SyncResult` field mapping to `SyncAllResult` (resolved via codebase inspection)

**Decision**: `SyncResult(int ReportsCreated, IReadOnlyList<string> Errors)` maps to `SyncAllResult.MailboxesSynced` (count of mailbox groups iterated) and `SyncAllResult.AttachmentsDownloaded` (= `SyncResult.ReportsCreated`, which counts reports created from downloaded attachments).  
**Rationale**: The `SyncMailboxCommandHandler` iterates over importer groups by mailbox. `ReportsCreated` represents attachments successfully downloaded and stored as reports. The handler counts groups (`byMailbox.Count`) — this becomes `MailboxesSynced`.  
**Implementation note**: `SyncAllCommandHandler` tracks `byMailbox` group count from the sync step to populate `MailboxesSynced`. `AttachmentsDownloaded` comes from `SyncResult.ReportsCreated`.

### R-004 — Desktop ViewModel wiring pattern (resolved in clarify.md §Q4)

**Decision**: `SyncViewModel` is created via `ActivatorUtilities.CreateInstance<SyncViewModel>(provider, navigateToFilings)` — same pattern as `ReportsViewModel`.  
**Rationale**: Confirmed from `MainWindowViewModel` source — `ReportsViewModel` is wired identically with `ActivatorUtilities.CreateInstance<ReportsViewModel>(provider, navigateToFilings)`.  
**Implementation note**: `navigateToFilings` is `Action` (not `Action<Guid>` — no report-ID filter needed). The delegate sets `SelectedEntry` to the Filings `NavigationEntry`.

### R-005 — Navigation entry insertion position (resolved in clarify.md §Q4)

**Decision**: Insert `new NavigationEntry(Strings.Nav_Sync, syncVm)` between Reports and Settings in the `NavigationEntries` list.  
**Rationale**: Current order is `[Filings, Reports, Settings]`. Sync is inserted at index 2 → `[Filings, Reports, Sync, Settings]`.  
**Implementation note**: Change `NavigationEntries` initialisation in `MainWindowViewModel` constructor to include the Sync entry at the correct position.

### R-006 — ProcessReportsResult field mapping (resolved via codebase inspection)

**Decision**: `ProcessReportsResult(int FilingsCreated, int ReportsProcessed, int ReportsErrored, IReadOnlyList<string> Errors)` maps directly to `SyncAllResult.ReportsProcessed` and `SyncAllResult.FilingsCreated`.  
**Rationale**: Field names are semantically identical. `ReportsErrored` count is rolled into `SyncAllResult.Errors` as individual error strings.

### 1.4 Application Layer — Handler Implementation

#### `SyncAllCommandHandler`

```csharp
// src/Rentier.Application/Handlers/SyncAllCommandHandler.cs
using Rentier.Application.Commands;
using Rentier.Application.Common;
using Rentier.Application.DTOs;
using Rentier.Application.Interfaces;

namespace Rentier.Application.Handlers;

public sealed class SyncAllCommandHandler : ISyncAllCommandHandler
{
    private readonly ICommandHandler<SyncMailboxCommand, Result<SyncResult, Error>> _syncMailboxHandler;
    private readonly ICommandHandler<ProcessReportsCommand, Result<ProcessReportsResult, Error>> _processReportsHandler;

    public SyncAllCommandHandler(
        ICommandHandler<SyncMailboxCommand, Result<SyncResult, Error>> syncMailboxHandler,
        ICommandHandler<ProcessReportsCommand, Result<ProcessReportsResult, Error>> processReportsHandler)
    {
        _syncMailboxHandler = syncMailboxHandler;
        _processReportsHandler = processReportsHandler;
    }

    public async Task<Result<SyncAllResult, Error>> HandleAsync(
        SyncAllCommand command,
        IProgress<SyncProgressEntry> progress,
        CancellationToken ct = default)
    {
        var errors = new List<string>();
        var mailboxesSynced = 0;
        var attachmentsDownloaded = 0;
        var reportsProcessed = 0;
        var filingsCreated = 0;

        // Step 1: Mailbox sync
        progress.Report(new SyncProgressEntry(
            DateTimeOffset.Now,
            "Starting mailbox sync...",          // Strings.Sync_Progress_StartingMailboxSync
            SyncProgressSeverity.Info));

        // Bridge SyncProgress → SyncProgressEntry
        var internalProgress = new Progress<SyncProgress>(p =>
        {
            var entry = new SyncProgressEntry(
                DateTimeOffset.Now,
                p.CurrentFile ?? $"Processing {p.Processed}/{p.Total}",
                SyncProgressSeverity.Info);
            progress.Report(entry);
        });

        var syncResult = await _syncMailboxHandler.HandleAsync(
            new SyncMailboxCommand(internalProgress), ct);

        if (syncResult.IsSuccess)
        {
            attachmentsDownloaded = syncResult.Value.ReportsCreated;
            errors.AddRange(syncResult.Value.Errors);

            // Report warnings for non-fatal sync errors
            foreach (var err in syncResult.Value.Errors)
            {
                progress.Report(new SyncProgressEntry(
                    DateTimeOffset.Now, err, SyncProgressSeverity.Warning));
            }

            progress.Report(new SyncProgressEntry(
                DateTimeOffset.Now,
                $"Mailbox sync complete: {attachmentsDownloaded} attachment(s) downloaded",
                SyncProgressSeverity.Info));
        }
        else
        {
            var errorMsg = syncResult.Error.Message;
            errors.Add(errorMsg);
            progress.Report(new SyncProgressEntry(
                DateTimeOffset.Now, errorMsg, SyncProgressSeverity.Error));
        }

        // Step 2: Report processing (proceed even if sync had errors)
        progress.Report(new SyncProgressEntry(
            DateTimeOffset.Now,
            "Processing reports...",              // Strings.Sync_Progress_ProcessingReports
            SyncProgressSeverity.Info));

        var processResult = await _processReportsHandler.HandleAsync(
            new ProcessReportsCommand(), ct);

        if (processResult.IsSuccess)
        {
            reportsProcessed = processResult.Value.ReportsProcessed;
            filingsCreated = processResult.Value.FilingsCreated;
            errors.AddRange(processResult.Value.Errors);

            foreach (var err in processResult.Value.Errors)
            {
                progress.Report(new SyncProgressEntry(
                    DateTimeOffset.Now, err, SyncProgressSeverity.Warning));
            }

            if (reportsProcessed == 0)
            {
                progress.Report(new SyncProgressEntry(
                    DateTimeOffset.Now,
                    "No new reports to process.",
                    SyncProgressSeverity.Info));
            }
            else
            {
                progress.Report(new SyncProgressEntry(
                    DateTimeOffset.Now,
                    $"Processed {reportsProcessed} report(s), created {filingsCreated} filing(s)",
                    SyncProgressSeverity.Info));
            }
        }
        else
        {
            var errorMsg = processResult.Error.Message;
            errors.Add(errorMsg);
            progress.Report(new SyncProgressEntry(
                DateTimeOffset.Now, errorMsg, SyncProgressSeverity.Error));
        }

        // Step 3: Aggregate and return
        return Result<SyncAllResult, Error>.Success(
            new SyncAllResult(
                mailboxesSynced,
                attachmentsDownloaded,
                reportsProcessed,
                filingsCreated,
                errors.AsReadOnly()));
    }
}
```

**Orchestration note on `mailboxesSynced`**: The current `SyncMailboxCommandHandler` does not expose a count of mailbox groups iterated — it returns only `SyncResult(ReportsCreated, Errors)`. To correctly populate `SyncAllResult.MailboxesSynced`, the handler would need to return this count. Since we cannot modify `SyncMailboxCommandHandler`, `mailboxesSynced` will be set to `1` when the sync call succeeds (indicating at least one mailbox was processed) or `0` on failure. This is a known approximation — future enhancement could extend `SyncResult` with a `MailboxCount` field.

**Alternative**: Set `mailboxesSynced = syncResult.IsSuccess ? 1 : 0` as a simplification. The spec does not mandate per-mailbox count granularity in the progress log — only the summary. This is acceptable for MVP.

        };

#### `SyncViewModel`

```csharp
// src/Rentier.Desktop/ViewModels/SyncViewModel.cs
using System.Collections.ObjectModel;
using System.Reactive;
using System.Reactive.Concurrency;
using System.Reactive.Disposables;
using ReactiveUI;
using Rentier.Application.Commands;
using Rentier.Application.Common;
using Rentier.Application.DTOs;
using Rentier.Application.Interfaces;

namespace Rentier.Desktop.ViewModels;

public sealed class SyncViewModel : ReactiveObject, IActivatableViewModel
{
    public ViewModelActivator Activator { get; } = new();

    private readonly ISyncAllCommandHandler _syncHandler;
    private readonly Action _navigateToFilings;
    private readonly IScheduler _scheduler;

    private CancellationTokenSource? _cts;

    private bool _isRunning;
    private string? _summaryMessage;

    public bool IsRunning
    {
        get => _isRunning;
        private set => this.RaiseAndSetIfChanged(ref _isRunning, value);
    }

    public string? SummaryMessage
    {
        get => _summaryMessage;
        private set => this.RaiseAndSetIfChanged(ref _summaryMessage, value);
    }

    public ObservableCollection<SyncProgressEntryViewModel> LogEntries { get; } = new();

    public ReactiveCommand<Unit, Unit> SyncCommand { get; }
    public ReactiveCommand<Unit, Unit> CancelCommand { get; }

    public SyncViewModel(
        ISyncAllCommandHandler syncHandler,
        Action navigateToFilings,
        IScheduler? scheduler = null)
    {
        _syncHandler = syncHandler;
        _navigateToFilings = navigateToFilings;
        _scheduler = scheduler ?? RxApp.MainThreadScheduler;

        SyncCommand = ReactiveCommand.CreateFromTask(
            RunSyncAsync,
            outputScheduler: _scheduler);

        CancelCommand = ReactiveCommand.Create(
            () => _cts?.Cancel(),
            outputScheduler: _scheduler);

        // Bind IsRunning to SyncCommand.IsExecuting
        SyncCommand.IsExecuting.Subscribe(v => IsRunning = v);
    }

    private async Task RunSyncAsync(CancellationToken ct)
    {
        LogEntries.Clear();
        SummaryMessage = null;
        _cts = CancellationTokenSource.CreateLinkedTokenSource(ct);

        var progress = new Progress<SyncProgressEntry>(entry =>
        {
            _scheduler.Schedule(() =>
                LogEntries.Add(SyncProgressEntryViewModel.From(entry)));
        });

        try
        {
            var result = await _syncHandler.HandleAsync(
                new SyncAllCommand(), progress, _cts.Token);

            if (result.IsSuccess)
            {
                var r = result.Value;
                var summaryParts = new List<string>();
                if (r.AttachmentsDownloaded > 0)
                    summaryParts.Add($"{r.AttachmentsDownloaded} attachment(s) downloaded");
                if (r.ReportsProcessed > 0)
                    summaryParts.Add($"{r.ReportsProcessed} report(s) processed");
                if (r.FilingsCreated > 0)
                    summaryParts.Add($"{r.FilingsCreated} filing(s) created");
                if (r.Errors.Count > 0)
                    summaryParts.Add($"{r.Errors.Count} error(s)");

                SummaryMessage = summaryParts.Count > 0
                    ? $"Sync complete: {string.Join(", ", summaryParts)}"
                    : "Sync complete: nothing to process";

                // Auto-navigate to Filings if filings created and no errors
                if (r.FilingsCreated > 0 && r.Errors.Count == 0)
                    _navigateToFilings();
            }
            else
            {
                SummaryMessage = $"Sync failed: {result.Error.Message}";
            }
        }
        catch (OperationCanceledException)
        {
            _scheduler.Schedule(() =>
                LogEntries.Add(SyncProgressEntryViewModel.From(
                    new SyncProgressEntry(
                        DateTimeOffset.Now,
                        "Sync cancelled by user",
                        SyncProgressSeverity.Info))));
            SummaryMessage = "Sync cancelled by user";
        }
        finally
        {
            _cts?.Dispose();
            _cts = null;
        }
    }
}
```
