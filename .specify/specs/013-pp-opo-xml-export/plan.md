# Implementation Plan: PP-OPO XML Export

**Branch**: `feature/013-pp-opo-xml-export` | **Date**: 2026-04-07 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `.specify/specs/013-pp-opo-xml-export/spec.md`

---

## Summary

Add a dedicated "Export" button column to the FilingsView DataGrid that serializes a single
PP-OPO tax filing into a valid ePorezi XML file and writes it to a user-chosen path via the
Avalonia 11 native save dialog. The feature spans three layers:

- **Application**: New `ExportFilingCommand(Guid FilingId)` record, `IXmlFilingSerializer`
  interface, and `ExportFilingCommandHandler` that loads `Filing → Report → Importer →
  TaxpayerProfile` via four repositories and returns `Result<byte[], Error>`.
- **Infrastructure**: `PpOpoXmlSerializer` implementing `IXmlFilingSerializer` using
  `System.Xml.Linq` (`XDocument`); registered as `AddTransient` in
  `InfrastructureServiceExtensions`.
- **Desktop**: `FilingsViewModel` gains `ExportCommand` (`ReactiveCommand<Guid, Unit>`);
  `FilingsView.axaml` gains an "Export" DataGrid column. File write uses
  `StorageProvider.SaveFilePickerAsync`. Handler registered in
  `CompositionRoot.AddDesktopServices()`.

No Domain changes. No EF Core migration. All existing entities are read-only by this feature.

---

## Technical Context

**Language/Version**: C# 12 / .NET 8  
**Primary Dependencies**: Avalonia UI 11, ReactiveUI, System.Xml.Linq, Microsoft.Extensions.DependencyInjection  
**Storage**: Read-only from existing SQLite via EF Core 8 — no new tables or columns  
**Testing**: xUnit + FluentAssertions + NSubstitute; SQLite in-memory for infrastructure tests  
**Target Platform**: Windows + macOS desktop (cross-platform Avalonia)  
**Project Type**: Desktop application (Avalonia MVVM)  
**Performance Goals**: Export round-trip ≤ 3 s from click to file saved (SC-001)  
**Constraints**: No UI thread blocking; decimal for money; DateOnly for dates; all I/O async;
`AddTransient` only (root ServiceProvider pattern)  
**Scale/Scope**: Single-user SQLite; one filing exported at a time; no concurrent export

## Phase 0: Research

> All NEEDS CLARIFICATION items were resolved in `clarify.md` via static codebase analysis
> before planning. No external research or tooling decisions are blocked. Findings consolidated
> below for traceability.

### R-001 — Entity loading chain and null-ReportId path (resolved in clarify.md §Decision 1)

**Decision**: Four repositories in sequence: `IFilingRepository.GetByIdAsync` →
`IReportRepository.GetByIdAsync` (via `Filing.ReportId`) → `IImporterRepository.GetByIdAsync`
(via `Report.ImporterId`) → `ITaxpayerProfileRepository.GetAsync`.  
**Null handling**: If `Filing.ReportId` is `null`, skip `IReportRepository` and
`IImporterRepository`; treat `PaymentNotes` as `string.Empty`. Serialization continues normally.  
**Rationale**: All four repository interfaces already exist in `Rentier.Application.Repositories`
with `GetByIdAsync` / `GetAsync` methods sufficient for this use case. No new repository methods
needed.

### R-002 — `TaxpayerProfile.PhoneNumber` vs `Phone` field name correction

**Decision**: The spec and architecture rules reference `profile.Phone` but the actual domain
entity `TaxpayerProfile` exposes the property as `PhoneNumber` (nullable `string?`). The
serializer MUST use `profile.PhoneNumber ?? string.Empty` when writing the `<Telefon>` element.  
**Rationale**: Static code analysis of `TaxpayerProfile.cs` confirms the property name.
Documenting here to prevent a compile error during implementation.

### R-003 — `Importer.PaymentNotes` is non-nullable `string`

**Decision**: `Importer.PaymentNotes` is declared as `string` (not `string?`), defaulting to
`string.Empty`. When the importer is resolved, `importer.PaymentNotes` is used directly. When
the importer is unavailable (null ReportId or missing importer), `string.Empty` is used.  
**Rationale**: Static analysis of `Importer.cs` confirms the field type.

### R-004 — `ExportFilingCommand` return type (resolved in clarify.md §Decision 2)

**Decision**: `Result<byte[], Error>` using the project's existing `Result<TValue, TError>`
and `Error` types from `Rentier.Application.Common`.  
**Rationale**: Consistent with every other command handler in the codebase (e.g.,
`UpdateFilingStatusCommand` returns `Result<VoidResult, Error>`).

### R-005 — Avalonia 11 save dialog API (resolved in clarify.md §Decision 3)

**Decision**: `StorageProvider.SaveFilePickerAsync(new FilePickerSaveOptions { ... })` on the
top-level window obtained via `TopLevel.GetTopLevel(view)?.StorageProvider`.  
`Avalonia.Controls.SaveFileDialog` is explicitly prohibited.  
**Rationale**: Legacy `SaveFileDialog` is removed/broken in Avalonia 11; `StorageProvider` is
the supported API.

### R-006 — `System.Xml.Linq` XML serialization approach

**Decision**: Build the XML document using `XDocument` with `XElement` and use CDATA sections
via `XCData` for `FullName` and `Address` fields.  
**Rationale**: `System.Xml.Linq` is already identified in the constitution Technology Stack
table for XML serialization. `XDocument.Save(stream, SaveOptions.None)` produces a UTF-8
document with the XML declaration.  
**Alternative considered**: `XmlWriter` — rejected for verbosity; `System.Text.Json` — not
applicable. `XDocument` provides sufficient abstraction for the fixed PP-OPO schema.

### R-007 — DI registration location (resolved in spec + architecture rules)

**Decision**: `ExportFilingCommandHandler` registered in `CompositionRoot.AddDesktopServices()`
(not `InfrastructureServiceExtensions`). `PpOpoXmlSerializer` registered in
`InfrastructureServiceExtensions.AddInfrastructureServices()` as
`AddTransient<IXmlFilingSerializer, PpOpoXmlSerializer>()`.  
**Rationale**: Follows the existing pattern — filing handlers are in CompositionRoot (see
comment in existing code: "Filing handlers — registered in CompositionRoot"), while
infrastructure services/serializers live in `InfrastructureServiceExtensions`.

### R-008 — XML encoding and declaration

**Decision**: UTF-8 with XML declaration (`<?xml version="1.0" encoding="utf-8"?>`). Use
`Encoding.UTF8` when calling `XDocument.Save`.  
**Rationale**: Spec assumption §XML encoding explicitly requires UTF-8 with declaration.
`XDocument.Save` to a `MemoryStream` with `new UTF8Encoding(false)` writer produces correct
output without BOM.

### R-009 — `SifraVrstePrihoda` mapping

**Decision**: `IncomeType.Interest → 111401000`, `IncomeType.Dividend → 111402000`.  
**Rationale**: Directly specified in FR-006 and verified in spec acceptance scenarios 4 and 5.

### R-010 — No new EF Core migration (resolved in clarify.md §Decision 5)

**Decision**: Zero database changes. All required entities (`Filing`, `Report`, `Importer`,
`TaxpayerProfile`) are already persisted by existing migrations.  
**Rationale**: The feature is read-only with respect to the database.

## Phase 1: Design & Contracts

### Entities Used (read-only)

See `data-model.md` for the full entity field inventory and XML mapping table.

No Domain entity changes. No new DTOs required — the handler works directly with domain
entities and passes a flat parameter set to `IXmlFilingSerializer`.

### Interface Design

#### `IXmlFilingSerializer` (Application layer)

Defined in `Rentier.Application.Interfaces`:

```csharp
/// <summary>
/// Serializes a PP-OPO filing and taxpayer context into a UTF-8 XML byte array
/// conforming to the ePorezi PP-OPO schema.
/// </summary>
public interface IXmlFilingSerializer
{
    /// <summary>
    /// Returns the serialized XML bytes for the given filing context.
    /// </summary>
    /// <param name="filing">The filing aggregate root.</param>
    /// <param name="profile">The taxpayer profile (must not be null).</param>
    /// <param name="paymentNotes">Importer payment notes; empty string if unavailable.</param>
    byte[] Serialize(Filing filing, TaxpayerProfile profile, string paymentNotes);
}
```

The method is synchronous — `XDocument` serialization is CPU-only and never touches I/O. The
async boundary is at the handler level (DB reads) and at the Desktop level (file write).

#### `ExportFilingCommand` (Application layer)

```csharp
public sealed record ExportFilingCommand(Guid FilingId);
```

Handler signature:

```csharp
public sealed class ExportFilingCommandHandler
    : ICommandHandler<ExportFilingCommand, Result<byte[], Error>>
{
    Task<Result<byte[], Error>> HandleAsync(ExportFilingCommand command, CancellationToken ct);
}
```

#### Handler loading logic

```
1. await _filingRepo.GetByIdAsync(command.FilingId, ct)
     → null  → return Failure(Error.NotFound("Filing not found."))
2. await _profileRepo.GetAsync(ct)
     → null  → return Failure(Error.Domain("Taxpayer profile is required before exporting."))
3. if filing.ReportId is not null:
       await _reportRepo.GetByIdAsync(filing.ReportId.Value, ct)   (may be null → ignore)
       if report is not null:
           await _importerRepo.GetByIdAsync(report.ImporterId, ct) (may be null → ignore)
4. paymentNotes = importer?.PaymentNotes ?? string.Empty
5. return Success(_serializer.Serialize(filing, profile, paymentNotes))
```

#### `FilingsViewModel` export integration (Desktop layer)

New constructor parameter:

```csharp
ICommandHandler<ExportFilingCommand, Result<byte[], Error>> exportFiling,
Func<Guid, Task> exportFileWriter   // injected delegate: wraps StorageProvider + disk write
```

New command:

```csharp
public ReactiveCommand<Guid, Unit> ExportCommand { get; }
```

Initialization:

```csharp
ExportCommand = ReactiveCommand.CreateFromTask<Guid>(
    async (filingId, ct) =>
    {
        var result = await _exportFiling.HandleAsync(new ExportFilingCommand(filingId), ct);
        if (!result.IsSuccess)
        {
            ErrorMessage = result.Error.Message;
            return;
        }
        await _exportFileWriter(filingId, result.Value);
    },
    outputScheduler: _scheduler);
```

> **Note**: The `exportFileWriter` delegate is supplied by `CompositionRoot` and captures the
> Avalonia `StorageProvider` to keep `FilingsViewModel` testable (no Avalonia UI dependency in
> the ViewModel). The delegate opens the save dialog, writes bytes, and handles cancellation
> silently (no error when user dismisses dialog). See contracts for the delegate signature.

#### `PpOpoXmlSerializer` (Infrastructure layer)

Implements `IXmlFilingSerializer` using `System.Xml.Linq`. Key responsibilities:

1. Map `IncomeType` to `SifraVrstePrihoda` (`Interest → 111401000`, `Dividend → 111402000`).
2. Format all `decimal` fields with `"F2"` and `CultureInfo.InvariantCulture`.
3. Format `DateOnly` fields: `IncomeDate.ToString("yyyy-MM-dd")`,
   `FilingDeadline.ToString("yyyy-MM-dd")`, `IncomeDate.ToString("yyyy-MM")`.
4. Wrap `FullName` and `Address` in `XCData`.
5. Serialize `XDocument` to `byte[]` via `MemoryStream` with `new UTF8Encoding(false)` (no BOM).

#### `CompositionRoot` additions

```csharp
// Export handler
services.AddTransient<
    ICommandHandler<ExportFilingCommand, Result<byte[], Error>>,
    ExportFilingCommandHandler>();

// Export file-writer delegate (owns StorageProvider + disk write)
services.AddTransient<Func<Guid, byte[], Task>>(provider =>
    async (filingId, bytes) =>
    {
        var window = /* resolve top-level window */;
        var file = await window.StorageProvider.SaveFilePickerAsync(new FilePickerSaveOptions
        {
            Title = "Save PP-OPO XML",
            SuggestedFileName = /* PP-OPO_YYYY-MM_JMBG.xml derived from bytes or filing */,
            FileTypeChoices = new[] { new FilePickerFileType("XML Files") { Patterns = ["*.xml"] } }
        });
        if (file is null) return; // user cancelled — no error shown
        await using var stream = await file.OpenWriteAsync();
        await stream.WriteAsync(bytes);
    });
```

> **Implementation note**: `SuggestedFileName` requires knowledge of the filing's period and
> JMBG. Two options: (a) the `ExportFilingCommand` handler returns a richer DTO containing
> `(byte[] Bytes, string SuggestedFileName)`, or (b) the Desktop delegate derives the filename
> from the bytes themselves (not practical). **Preferred**: the handler returns a
> `Result<ExportFilingResult, Error>` where `ExportFilingResult` is a record with `Bytes` and
> `SuggestedFileName`. See contracts for the updated record definition.

#### Revised return type: `ExportFilingResult`

```csharp
// Application/Commands/ExportFilingResult.cs
public sealed record ExportFilingResult(byte[] Bytes, string SuggestedFileName);
```

Handler returns `Result<ExportFilingResult, Error>`. The `SuggestedFileName` is constructed in
the handler as:

```csharp
var period = filing.IncomeDate.ToString("yyyy-MM");
var suggestedName = $"PP-OPO_{period}_{profile.Jmbg}.xml";
```

This keeps the filename derivation logic in the Application layer where JMBG and IncomeDate
are available, and the Desktop layer simply passes the string to `SaveFilePickerAsync`.
